# Releasing RelayDisplay

How a signed build reaches a phone. Written for the repository owner, because signing is the one
part of this project that cannot be undone if it goes wrong.

---

## 1. The signing key

An Android app's identity **is** its signing key. Android will only install an update signed by
the same key that signed the installed version. Lose the key and you cannot ship an update to
anyone who already has the app — they must uninstall and reinstall, losing their pairing and
settings.

### Generate it — once, yourself

```bash
keytool -genkeypair -v \
  -keystore ~/private/relay-display-app-signing.jks \
  -alias relay-display \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=Avinash Kumar, O=RelayDisplay, C=IN"
```

- **10 000 days** (~27 years). Play requires a key valid well past 2033.
- **RSA 4096**, comfortably above the 2048 minimum.
- Choose a long random passphrase and let `keytool` prompt for it. Do not put it in the command.

> The key is generated **only by you**, on your own machine. It is never generated by CI, never
> committed, never pasted into a chat, an issue, a log or a commit message.

### Protect it

- Keep it outside the repository. `~/private/` or an encrypted volume.
- **At least two encrypted backups** in different places — for example an encrypted external disk
  and an encrypted cloud archive.
- Store the **passphrase separately from the keystore**. A backup containing both is one theft
  away from being useless as a protection.
- Record the certificate fingerprint (below) somewhere you can find it; it is public and is what
  lets you detect a substituted key.

### Read the fingerprint

```bash
keytool -list -v \
  -keystore ~/private/relay-display-app-signing.jks \
  -alias relay-display | grep 'SHA256:'
```

Copy the `SHA256:` value. It is **not** a secret — it is published in every APK you ship. It goes
into the `ANDROID_SIGNING_CERT_SHA256` repository variable, and the release workflow fails if a
build is ever signed by anything else.

### Base64-encode it for GitHub (macOS)

```bash
base64 -i ~/private/relay-display-app-signing.jks | tr -d '\n' | pbcopy
```

This writes nothing to disk and leaves a single-line value on your clipboard.

> Paste it **only** into the `ANDROID_SIGNING_KEY_BASE64` secret field. Nowhere else. Not into a
> file in this repository, not into a terminal you have scrollback for, not into a chat. After
> pasting, copy something harmless to clear your clipboard.

## 2. GitHub setup

Do this once.

### Environment and secrets

1. **Settings → Environments → New environment**, named exactly `release`.
2. Add these four **environment secrets**:

   | Secret | Value |
   |---|---|
   | `ANDROID_SIGNING_KEY_BASE64` | the single-line Base64 from above |
   | `ANDROID_KEYSTORE_PASSWORD` | keystore passphrase |
   | `ANDROID_KEY_ALIAS` | `relay-display` |
   | `ANDROID_KEY_PASSWORD` | key passphrase (often the same as the keystore one) |

3. Add one **environment variable** (not a secret):

   | Variable | Value |
   |---|---|
   | `ANDROID_SIGNING_CERT_SHA256` | the `SHA256:` fingerprint |

   Colons and case do not matter; the workflow normalises it.

4. Under the environment's **Deployment protection rules**, add yourself as a **required
   reviewer** if your plan supports it. Then no signed build starts without you approving it,
   even if someone pushes a tag.

Putting the secrets on the environment rather than the repository is what stops the CI workflow —
or any future workflow — from reading them. Only jobs that declare `environment: release` can.

### Repository hardening

5. **Settings → Actions → General → Workflow permissions**: set **Read repository contents
   permission**. Each workflow requests what it needs; the release workflow grants
   `contents: write` to its publishing job alone.
6. **Settings → Rules → Rulesets → New branch ruleset** for `main`:
   - Require a pull request before merging
   - Require status checks: select the **CI** workflow
   - Block force pushes
   - Restrict deletions
7. **New tag ruleset** targeting `v*`:
   - Restrict creations to yourself
   - Restrict deletions and updates

Step 7 matters more than it looks: the release workflow triggers on `v*` tags, so control of tag
creation is control of releases.

## 3. Cutting a release

Version numbers live in `gradle.properties` and nowhere else. The pipeline never edits them —
bumping a version is a reviewable change, not something a robot does behind you.

1. Edit `gradle.properties`:
   - `APP_VERSION_CODE` — **strictly larger** than any previously released or uploaded value.
   - `APP_VERSION_NAME` — `1.0.0`, or `0.1.0-beta.1` for a prerelease.
2. Update release notes or a changelog if you keep one.
3. Open a pull request.
4. Wait for CI to pass.
5. **Run the physical two-phone smoke test below.** CI cannot do this.
6. Merge into `main`.
7. Pull the exact merged commit:
   ```bash
   git checkout main && git pull --ff-only
   ```
8. Create an annotated tag matching the version exactly:
   ```bash
   git tag -a v0.1.0-beta.1 -m "Relay Display 0.1.0-beta.1"
   ```
9. Push **only** the tag:
   ```bash
   git push origin v0.1.0-beta.1
   ```
10. Watch the **Release** workflow. Approve the `release` environment if you configured a
    reviewer.
11. Download the published APK from the release page.
12. Verify it before installing:
    ```bash
    sha256sum -c SHA256SUMS
    ```
13. Install on both phones and check the app opens and pairs.

> Never build a release from a feature branch. The workflow enforces this — a tag whose commit is
> not contained in `origin/main` fails the ancestry check.

### If the tag was wrong

Delete it locally and remotely, fix the version, and tag again. The workflow refuses to overwrite
an existing GitHub Release, so a botched publish needs the release deleted in the UI first.

## 4. Physical release checklist

**These are manual. Nothing in CI runs them, and a passing pipeline is not evidence any of them
were performed.** This app's whole purpose is two phones talking to each other; an emulator
cannot tell you it works.

Devices: **S22 Ultra as Controller**, **Lenovo K6 Power / K33a42 (API 24) as Companion Display**.

Pairing and connection:

- [ ] Pair over shared Wi-Fi, comparing the six-digit code on both screens
- [ ] Pair over the S22's hotspot with the Lenovo joined to it
- [ ] Reconnect automatically after Wi-Fi is turned off and on
- [ ] Role switch Controller → Display and back; both dashboards correct afterwards

Content:

- [ ] Send text; Copy on the Display puts it on the clipboard; Close returns to the waiting screen
- [ ] Send a QR code; it scans from another phone; Close works
- [ ] Send an image; it arrives and displays

Mirroring — the part that has broken before:

- [ ] Mirror for **15–30 minutes continuously** with a moving screen
- [ ] **Press Home and use another app** while mirroring; the session must survive
      (this exact case previously killed the session within seconds)
- [ ] Stop sharing from the Controller dashboard card
- [ ] Close the presentation from the Display; the Controller stops capturing
- [ ] Kill the Display app while mirroring; the Controller stops capturing within a few seconds
- [ ] **After every stop, confirm the capture indicator is gone** from the status bar

Lifecycle:

- [ ] Background and foreground both apps
- [ ] Screen off and on
- [ ] Battery optimisation: confirm behaviour with the app both exempted and not
- [ ] No stale MediaProjection notification after any disconnection

Distribution:

- [ ] Clean install of the new APK on a device with no previous version
- [ ] **Upgrade over the previous signed release** — this proves the signing key is unchanged; if
      it fails with a signature mismatch, stop and do not publish

## 5. Play Store compatibility

Not implemented yet. Recorded so the decisions are made deliberately rather than discovered.

- The `applicationId` is `com.avinash.relaydisplay` and must never change. It is the identity Play
  and every installed device use.
- For seamless updates across GitHub APKs and Play, **the same app-signing key must sign both.**
  When enrolling in Play App Signing, you would provide this existing key as the app-signing key.
- Play then issues a separate **upload key**. Once that exists:
  - the Play AAB pipeline signs with the **upload key**;
  - GitHub APKs continue to sign with the **app-signing key**;
  - Play re-signs uploads with the app-signing key before distribution, so users see one
    consistent signature.
- Every Play upload needs a **strictly larger `APP_VERSION_CODE`**. Play permanently rejects a
  versionCode it has already seen — there is no way to reuse one.
- Automated Play publishing is **not** configured. Adding it means a service account key, which is
  a second secret with its own blast radius; do it separately and deliberately.

## 6. What the pipeline actually guarantees

Worth being precise, because "the build passed" is not the same as "this is safe to ship".

It does check:

- the tag equals `v${APP_VERSION_NAME}` from source
- the tagged commit is contained in `origin/main`
- no GitHub Release already exists for that tag
- all four signing secrets and the fingerprint variable are present, before decoding anything
- the APK verifies under APK Signature Scheme v2
- the APK's certificate SHA-256 equals `ANDROID_SIGNING_CERT_SHA256`
- the APK's applicationId, versionCode and versionName match the source
- the AAB verifies with `jarsigner`
- unit tests and `lintRelease` pass, and instrumentation tests **compile**

It does **not** check:

- that instrumentation tests **pass** — they need a device; nothing in CI runs them
- anything about real two-phone behaviour
- byte-for-byte reproducibility — this is **not** claimed. Android signing embeds timestamps, and
  reproducibility has not been demonstrated for this project
- that the APK installs as an upgrade over the previous release — that is the manual check above
